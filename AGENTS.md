# AGENTS.md

## Project
- Rust (edition 2024) auth API: `POST /api/register`, `POST /api/login`, `POST /api/logout`, `GET /api/me`, and account linking (`POST /api/link/start`, `GET /api/link`, `DELETE /api/link/{uuid}`, `POST /internal/link/claim`) on axum 0.8 + sqlx (Postgres) + argon2.
- All backend code lives in `src/main.rs` (no lib/module split). sqlx uses **runtime** queries, not `query!` macros — so there is no compile-time DB dependency.
- Everything else falls through to the static React build at `frontend/dist` (single `ServeDir` fallback route).
- A Caddy reverse proxy (`proxy` service, `dhi.io/caddy`, config in `Caddyfile`) terminates TLS and is the **only** published web service (host 80/443 → container 8080/8443). `app` publishes no ports — reach it through the proxy.
- A Minecraft stack runs alongside it: `velocity` (proxy) + `purpur` (backend), with **AuthMe** for in-game authentication and **LinkBridge** (a small Java plugin in `plugin/`) for account linking. See the Minecraft and LinkBridge sections below.
- Everything runs in Docker. The web stack uses hardened `dhi.io` images (requires `docker login dhi.io` first); the Minecraft services use community `itzg` images — a deliberate provenance tradeoff.

## Commands
- Run app: `docker compose --env-file .env.docker up --build -d` (served by the proxy at `https://localhost`; plain `http://localhost` 308-redirects to it)
- Run tests: `docker compose --env-file .env.docker run --rm tests`
- Build the Minecraft link plugin: `./scripts/build-plugin.sh` — Gradle in a container; installs the jar into `mc/purpur/plugins/`
- First-run Minecraft setup: `./scripts/mc-init.sh` — creates `.env.docker` if missing, generates `VELOCITY_SECRET` and `LINK_SERVICE_TOKEN`, creates `mc/`
- Export the whole stack: `./scripts/export.sh` — repo + `mc/` + a Postgres dump into `project-export-<timestamp>.tar.gz`
- Quick compile check: `cargo check --tests` — **the arbiter of truth. Never trust a claim about this code; verify it with this command.** It needs no running database, so it works on the host.
- DB shell: `docker compose --env-file .env.docker exec db psql -U postgres -d project_db`

## Environment & database
- `.env.docker` (never commit): `POSTGRES_PASSWORD`, `DATABASE_URL` (points at the `db` container hostname — it only resolves on the Compose network, so backend work must go through Compose, not host `cargo run`/`cargo test`), and `SITE_ADDRESS` (the proxy's public hostname; `localhost` uses Caddy's internal CA, a real domain triggers automatic Let's Encrypt). On a fresh clone create it from `.env.docker.example` and set your own password in both values. URL-encode special chars in passwords.
- `dotenvy::dotenv()` loads `.env` for non-Compose runs; Compose injects `.env.docker` via `env_file`. Keep the two in mind when a variable is missing.
- Schema lives in `migrations/` and is applied by sqlx automatically in `connect()` (runtime `Migrator`; reads `./migrations` relative to the process CWD — the Dockerfile copies it into the runtime image). Add a new numbered file; never edit an already-applied migration.
- `users` (`0001`): `id` identity PK, `name`, `surname`, `login` (UNIQUE), `login_displayed`, `email` (UNIQUE), `password_hash`; all TEXT NOT NULL. `sessions` (`0002`): `user_id` FK ON DELETE CASCADE, `token_hash` (UNIQUE), `created_at`, `expires_at`, `ip`, `user_agent`. `auth_rate_limits` (`0003`): `(scope, subject)` PK, `window_index`, `count` — per-IP fixed-window counters. `login_failures` (`0003`): `email` PK REFERENCES `users(email)` ON DELETE CASCADE, `failed_count`, `first_failed_at`, `locked_until`. `link_codes` (`0004`): `user_id` FK ON DELETE CASCADE, `code_hash` (UNIQUE), `created_at`, `expires_at`, `used_at`. `minecraft_accounts` (`0004`): `user_id` FK ON DELETE CASCADE, `uuid` (UNIQUE), `username`, `linked_at`. `audit_log` (`0004`): append-only `event`, `user_id` (nullable, **no** FK — the log outlives users), `detail`, `ip`.
- Postgres string comparison is case-sensitive; email/login lookups rely on the app-level normalization below, not on the database.

## API semantics
- Register: `201` created · `400` validation failure · `409` email or login already taken.
- Login: `200` success · `401` unknown email OR wrong password (intentionally identical — do not leak which accounts exist).
- Logout: `200` always; deletes the session row and clears the cookie (idempotent, no session required).
- Me: `200` with the current user, or `401` when the session cookie is missing, unknown, or expired.
- Rate limiting: `/api/login` and `/api/register` return `429` with a `Retry-After` header when the client IP is over its window budget. A locked account is **not** a `429` — it returns the ordinary `401`, indistinguishable from a wrong password.
- Linking: `POST /api/link/start` → `200 {code, expires_in}` (session). `GET /api/link` → `200 {accounts}`. `DELETE /api/link/{uuid}` → `204`, or `404` if it is not yours. `POST /internal/link/claim` (service token) → `200`; `404` for an unknown, used, or expired code (all identical); `409` when the UUID is already linked (the code is **not** consumed); `401` for a bad token; `503` when `LINK_SERVICE_TOKEN` is unset. `POST /internal/link/status` (service token) → `200` when the UUID is linked, `404` when it is not, `400` for a malformed UUID — bare codes and no body, so the plugin never parses JSON.

## Conventions (follow these)
- `email` and `login` are normalized to **lowercase on write (register) and on read (login)**. `login_displayed` stores the original casing. Never add a lookup or write that skips normalization.
- Duplicate handling has two layers, **both required**: an early `SELECT 1 ... WHERE email=$1 OR login=$2` → 409, plus `is_unique_violation()` → 409 on the INSERT. The constraint is the real check; the SELECT is only an optimization (race window).
- Validation: name/surname/login/email non-empty after trim; login = ASCII alphanumeric + `_!@`; email via `email_address::EmailAddress::is_valid`; password at least 15 chars.
- Passwords: `Argon2::default()`, hash before INSERT, verify on login.
- Sessions: token = 32 random bytes (`getrandom::fill`) hex-encoded; store only its `sha2` SHA-256 in `token_hash`, never the raw token. 24h absolute TTL (`SESSION_TTL_HOURS`). Cookie `session=...; HttpOnly; Path=/; SameSite=Lax` with `Secure` unless `COOKIE_SECURE=false`. Protected handlers take the `SessionUser` extractor.
- Rate limiting/lockout: per-IP fixed windows live in `auth_rate_limits` (subject = `client_ip`, which trusts the `X-Real-IP` Caddy overwrites), enforced by `from_fn_with_state` middleware on `/api/login` and `/api/register`. Per-account backoff lives in `login_failures`, keyed by the normalized email. Never make a locked account distinguishable from a wrong password, and never record failures for unknown emails (unbounded table growth). Knobs: `LOGIN_IP_*`, `REGISTER_IP_*`, `LOCKOUT_*`.
- Linking: codes are single-use, stored only as `hash_token` (SHA-256), newest-only per user, TTL `LINK_CODE_TTL_SECONDS` (300). `claim_link` marks `used_at` inside a transaction so exactly one claim wins; a `409` (UUID already linked) rolls back and leaves the code usable. The service token is compared as SHA-256 digests with `constant_time_eq`, and the endpoint answers `503` when `LINK_SERVICE_TOKEN` is unset (fail closed). The panel stores only `user_id ↔ uuid/username` — never a Minecraft password.

## Frontend
- React 19 + Vite 8 + react-router in `frontend/src` (routes `/` → `/cabinet`, `/register`, `/login`, `/cabinet` behind `RequireAuth`, `*` → `/`); no frontend tests. Its checks are `npm run build` (`tsc -b && vite build`) and `npm run lint`.
- Built only inside Docker (`Dockerfile` is multi-stage: node `npm ci` + `npm run build` → Rust `cargo build --release` → `dist` copied into the runtime image). `frontend/dist` is gitignored and produced by the image build.
- API calls use relative `/api/...` and there is **no Vite dev proxy**, so `npm run dev` alone cannot reach the backend — rebuild and use the Compose stack at `https://localhost`.
- Deep links work: the router's fallback is `ServeDir::new("frontend/dist").fallback(get(spa_fallback))`, which hands back the shell for any path that is not a real file. A path whose last segment has an extension is treated as a file and keeps its `404`, so a stale shell pointing at a removed chunk fails loudly instead of returning HTML where JavaScript was expected. `spa_fallback` also sets `Cache-Control: no-cache` — the shell names the hashed assets, so it must never be cached stale.
- The world is the game's own. Three committed assets carry it, and each has constraints that are not obvious:
  - `frontend/src/assets/fonts/minecraft.ttf` — "Minecraft Rus", © 2004–2012 BOGDAN Software. One weight, drawn on an **8px em** (a stem is exactly 1/8 em), so every `--step-*` is a multiple of 4 to stay on that grid at 1× and 2×; an off-grid size goes soft. Body sets `font-synthesis: none` because a synthesised bold smears the pixels, so hierarchy is size/colour/case and **nothing may ask for `font-weight: 600`**. `-webkit-font-smoothing: none` keeps the glyphs snapped.
  - `frontend/src/assets/dirt.png` — the 16×16 dirt block, tiled at 64px with `image-rendering: pixelated` under `--dirt-scrim`. Tune the scrim against the texture's **brightest speckle** (185,135,135), not its mean: bone on the raw block is 1.6:1. Text on the dirt also gets a hard 1px shadow, which is switched off on every widget — `.entry`, `.claim`, `.panel`, `.code`, `.field input`, `.btn`, `.note`, `.lamp` — because those have their own ground.
  - `frontend/src/assets/wood.png` — the 16×16 oak planks block, worn by `.code` only, tiled at 32px (a 16px texture at GUI scale 2) under `--wood-scrim`. The planks span only **3:1** end to end (`#67502c`→`#c29d62`), so *no* type colour clears 4.5:1 on the raw block — white is 2.5:1, ink 2.2:1. The 45% scrim takes the brightest plank down until white clears it (6.1:1) and keeps the grain and the seams. The `/link <code>` chips stay the `#373737` inset they always were; the wood is only for the code you copy out.
- **Every box is a Minecraft widget**, built from the game's own sprite colours. The chrome is a 1px `#000000` outline with a 2px bevel inside it (the sprite's 1px bevel at the game's default GUI scale of 2), declared once in `index.css` for the raised set (`.entry`, `.claim`, `.panel`, `.btn`, `.note`) and the sunken set (`.field input`, `.code`, `.lamp`). A component sets only its own face and type — a local `border` or base `box-shadow` silently overrides the shared chrome, because `App.css` loads after `index.css`.
  - Colours are **sampled from the 1.20.2 sprites, not guessed**: face `#6f6f6f`, bevel `#aaaaaa`/`#565656`, outline `#000000`; the highlighted sprite is `#757575` with `#afafaf`/`#5c5c5c` and a **white** outline; the disabled sprite is `#2c2c2c` with `#2b2b2b`/`#292929`. Hover is the highlighted sprite (the white outline is how the game says "this one") and disabled is a different face, not a faded live button.
  - **The primary button is `#c6c6c6`**, the container chrome's light grey, with `--ink` type — the only widget face light enough for dark text. It is the one emphasised action per screen; an amber primary was tried and rejected as the only off-palette thing on the page. Never introduce a new colour for emphasis.
  - `#6f6f6f` is mid-luminance, so **only white text clears 4.5:1 on it** (5.02:1) — no colour does (`--live` is 2.3:1). Widget text is therefore white and hierarchy is **size and case**, as in the game. Colour lives in **blocks and wells**: the lamp and the note's tone are blocks, and the entry's state chip is a `#373737` inset where green (5.5:1), red (5.2:1) and bone (8.6:1) come back. The code well is the one material surface — oak planks under `--wood-scrim`, white type, and `--amber-light` for the expiry (the page's `--amber` is far too dark for a scrimmed plank).
  - **Red means a problem, and there are two**: the account is **not linked** (`.entry[data-state='pending']` sets `--lamp: var(--down)`, so the lamp block and the chip both go red) and `.btn-danger` (Unlink) hovering. Green is linked. Nothing else is red.
  - **Data sits in a `.panel`** — the account details and the linked accounts each get a grey box so they rest on the game's surface instead of the dirt. A panel cannot dim its own text, so those tables use size and case (`dt` 12px uppercase tracked, `dd` 20px) rather than tone.
  - **No placeholders on the inputs.** On `#6f6f6f` the only AA placeholder is white, indistinguishable from typed text, so the email placeholders were removed rather than shipping an empty field that looks filled.
- `.topbar` is only a border; its contents live in `.topbar-inner`, which mirrors `.main`'s `--shell` width. Putting the padding on `.topbar` instead puts the wordmark on a different grid from the page — a 47px offset at 1086px, and 464px at 1920px.

## Minecraft (Velocity + Purpur)
- `velocity` (`itzg/mc-proxy`, `TYPE=VELOCITY`) is the only published Minecraft service (`25565`); `purpur` (`itzg/minecraft-server`, `TYPE=PURPUR`) publishes none and is reachable only through the proxy. Neither is a `dhi.io` image — community images, accepted with a provenance tradeoff.
- Offline ("cracked") mode on both sides: `online-mode = false` in `velocity.toml`, `ONLINE_MODE: "FALSE"` on the backend. Players are identified by offline UUIDs; the real gate is an in-game auth plugin.
- Modern forwarding: `player-info-forwarding-mode = "modern"` on Velocity; `proxies.velocity.{enabled,online-mode,secret}` in `paper-global.yml`. The secret comes from `VELOCITY_SECRET` in `.env.docker` (generated by `scripts/mc-init.sh`), is written to `mc/velocity/forwarding.secret`, and is interpolated into the backend config via `CFG_VELOCITY_SECRET`. Never commit it.
- Config layout: committed templates in `mc-config/` mounted read-only at `/config`; runtime state in `mc/` (gitignored) at `/server` (proxy) and `/data` (backend). `mc/` is the portable unit — worlds, plugins, jars, secrets.
- The backend sets `COPY_CONFIG_DEST=/data`, so `/config/<rel>` → `/data/<rel>` and `mc-config/purpur/` mirrors the server directory 1:1 (`config/paper-global.yml`, `plugins/AuthMe/config.yml`, `plugins/LinkBridge/config.yml`, …). Without that variable the attach point only reaches `/data/config`.
- **AuthMe** does in-game authentication — without it an offline server is impersonatable by anyone who types your name. Pinned by URL in `PLUGINS`. AuthMe 6.x ships **per-platform jars**; on Purpur use `AuthMe-6.0.1-Paper.jar` (not the Spigot/Folia/Bungee/Velocity ones).
- AuthMe's config is a **partial** file (`mc-config/purpur/plugins/AuthMe/config.yml`): ConfigMe fills every missing key from its defaults and rewrites the complete file, so only the keys we change are listed and it survives AuthMe upgrades. The `/config` sync overwrites the generated file each boot, so our values always win.
- `/link` must **never** be added to `settings.restrictions.allowCommands` — that list is for *unauthenticated* players. AuthMe already blocks all non-whitelisted commands before login; the plugin must additionally check `AuthMeApi.getInstance().isAuthenticated(player)`.
- `LINK_SERVICE_TOKEN` is generated by `scripts/mc-init.sh` and reaches the backend as `CFG_LINK_SERVICE_TOKEN` for the link plugin's config.
- `REPLACE_ENV_VARIABLES` / `REPLACE_ENV_DURING_SYNC` interpolate `${CFG_*}` only in files with the extensions `.yml`, `.yaml`, `.txt`, `.cfg`, `.conf`, `.properties` — extensionless files like `forwarding.secret` are **not** interpolated.
- `SYNC_SKIP_NEWER_IN_DESTINATION: "false"` forces the repo template to overwrite the server-generated config on every boot.
- `MC_VERSION` in `.env.docker` pins the backend version (`LATEST` or e.g. `26.3`); verified working with Purpur `26.3-2651`.

## LinkBridge plugin (`plugin/`)
- The in-game half of linking: `/link <code>` → `POST /internal/link/claim`. One class, no runtime dependencies, no state — the panel's `minecraft_accounts` table is the only record of a link, and the plugin never sees a password.
- After AuthMe authenticates a player, the plugin asks `POST /internal/link/status` and, only on `404`, tells them in chat that the account is not linked and where to link it (`panel-url`, which compose fills from `CFG_SITE_ADDRESS`). Any other answer — including an unreachable panel — is silent: a wrong "you are not linked" is worse than no message, and a linked player must never be nagged.
- Layout: `plugin/src/main/java/dev/mcpanel/linkbridge/LinkBridgePlugin.java`, `plugin/src/main/resources/{plugin.yml,config.yml}`, `plugin/build.gradle`, `plugin/settings.gradle`.
- Built by `./scripts/build-plugin.sh`: Gradle 9 in `gradle:jdk25`, nothing installed on the host. The jar is installed into `mc/purpur/plugins/` (gitignored, so it travels with the server data and the target host never needs a JDK). `plugin/` is the committed source; `plugin/build/`, `plugin/.gradle/` and `.plugin-build/` are ignored.
- `plugin.yml` declares `depend: [AuthMe]` and the command gates on `AuthMeApi.getInstance().isAuthenticated(player)`. That `getInstance()` returns **null** while AuthMe is not fully enabled, so the check must be `api == null || !api.isAuthenticated(player)` — fail closed. AuthMe's pre-login `allowCommands` whitelist is the other lock, and `/link` must stay out of it.
- Runtime config is `mc-config/purpur/plugins/LinkBridge/config.yml`: `api-base` (both `/internal` endpoints are derived from it), `panel-url: "https://${CFG_SITE_ADDRESS}/cabinet"`, `service-token: "${CFG_LINK_SERVICE_TOKEN}"`, `cooldown-seconds`, `timeout-seconds`. Keep placeholders out of its comments (see Traps).
- The JDK **must** match the backend's Java: `paper-api` 26.3 is Java 25 bytecode (class file major 69) and an older javac refuses to read it. Use Gradle, not raw `javac` — `paper-api` needs ~20 transitive jars (Adventure, annotations, bungee-chat, …) before its signatures resolve.
- The version lives in `plugin.yml` and is passed to Gradle as `-PpluginVersion`. Keep `paper-api` in `build.gradle` in step with `MC_VERSION`, and `AUTHME` in the script in step with `PLUGINS`.
- The panel answers with a bare status code (no body), so the plugin maps `200/400/401/404/409/503` to messages and never parses JSON. `404` covers unknown, used **and** expired codes on purpose.

## Testing (`#[cfg(test)] mod test` in src/main.rs)
- All tests hit real Postgres and run in parallel — they must be idempotent.
- Run via the Compose `tests` service (mounts the repo, runs `cargo test`): host `cargo test` cannot resolve the `db` hostname.
- Rules: random 16-char `Alphanumeric` identifier per run; emails as `test_{random}@example.com` **lowercased**; after every inserting sub-case, `DELETE ... WHERE email=$1` **before** the assert, binding the **stored (lowercase)** form — the cleanup value must match what the app stores, not the raw input.
- A new test must survive: repeated runs, parallel execution, and a run that failed mid-test (no leftover rows).

## Traps (learned the hard way)
- `rand` is **0.10**: `sample_iter` / `random_range` live on `RngExt`, not `Rng`; `random_string` / `random_char` were removed in 0.10 (they existed in 0.9). Build random strings with `sample_iter(Alphanumeric)`.
- tower-http 0.7's `ServeDir::not_found_service` wraps the fallback in `SetStatus` and **forces the response to `404`** — the correct body with the wrong status. An SPA needs `ServeDir::fallback`, which preserves the fallback's status. The old symptom was `/cabinet` returning the shell with a `404`, which browsers render anyway, so it looked fine while being a lie about the resource.
- `Alphanumeric` includes A–Z — anything bound directly to SQL (test cleanups, lookups) must be lowercased first.
- The `email_address` crate accepts single-label domains by default (`x@exa` is "valid") — do not assume TLD enforcement.
- `let _ = expr?;` is an antipattern — `?` already propagates the error; use the bare `expr?;`.
- Never run `docker compose down -v` — it deletes the `pgdata` volume and all database data. Plain `down` keeps it.
- Caddy in `dhi.io/caddy` runs as UID 65532, so it **cannot** bind 80/443: the `Caddyfile` sets `http_port 8080`/`https_port 8443` and Compose maps host 80/443 onto them. Do not "fix" the Caddyfile to listen on 80/443 — it will fail on a real Linux host (Docker Desktop happens to allow low ports, which hides the bug).
- The `tests` service is behind the `tests` Compose profile, so `up` never runs the suite; run it explicitly with `run --rm tests`.
- Caddy sends HSTS everywhere except `localhost` (matcher in `Caddyfile`) — otherwise a local `https://localhost` visit would force HTTPS on every other localhost dev server (e.g. Vite).
- Caddy **overwrites** `X-Real-IP` / `X-Forwarded-For` with the real peer address (verified: a spoofed value does not survive), so `client_ip` can trust them. Do not delete the `header_up X-Real-IP` line in the `Caddyfile`.
- Behind Docker Desktop every request reaches the app from one NAT address, so the per-IP limit acts globally on a Mac. That is an artifact of the local network, not a bug.
- Tests send a random `X-Real-IP` per request (see `send_from`) so the per-IP limiter cannot bleed across parallel tests; the rate-limit tests pass a fixed IP and clear their own rows.
- `rand` is test-only and lives in `[dev-dependencies]`; production randomness (session tokens) uses `getrandom::fill`.
- sqlx's runtime `Migrator` reads `./migrations` from the process CWD, so it only finds them when the app/tests start from the repo root (`/app`) — there is still no compile-time DB dependency.
- `.gitignore` ignores `AGENTS.md` itself and all `.env*` except the two `.example` files, so edits to this file never show up in `git status`.
- `/internal/*` is blocked **twice**: `handle /internal/* { respond 404 }` in the `Caddyfile` (so it is never public) and the `LINK_SERVICE_TOKEN` check in `claim_link`. Keep both. The `handle` blocks are deliberate — do not collapse them back into a bare `reverse_proxy`, or `/internal/link/claim` becomes reachable from the internet.
- `audit_log` has **no** FK to `users` (it must outlive them), so deleting a test user leaves its audit rows behind — tests use the `delete_user` helper, which removes audit rows for that user first.
- The `tests` service sets `LINK_SERVICE_TOKEN: test-service-token` in `compose.yaml`; without it the claim tests would get `503`. Host `cargo test` still lacks it.
- `mc-proxy` merges Velocity's bundled default `velocity.toml` **under** our file, and Velocity 4.x's default ships **uncommented** example `forced-hosts` (`lobby.example.com`, `factions.example.com`, …). Without an explicit empty `[forced-hosts]` (merged to `forced-hosts = {}`) Velocity refuses to start: "Server 'lobby' for forced host 'lobby.example.com' does not exist".
- `ci.pufferfish.host` — the only source the itzg image uses for `TYPE=PUFFERFISH` — returns `502`, and the project looks stale (no commits since 2025-12-21, branches stop at `ver/1.21`). `TYPE=PUFFERFISH` therefore crash-loops with `jq: syntax error … error code: 502`. Purpur is the stand-in; switching back is a one-line `TYPE` change.
- Do **not** name a Minecraft service `proxy` — the Caddy service owns that name. Minecraft's `25565` does not collide with Caddy's 80/443.
- Verified: a client connecting straight to the backend is answered with a `velocity:player_info` login-plugin request and dropped, while a login through Velocity returns Login Success. Keep the backend port unpublished — that plus forwarding is the whole trust model.
- AuthMe's `ProtectInventoryBeforeLogIn` is silently **disabled without PacketEvents** ("WARNING! The protectInventory feature requires PacketEvents! Disabling it..."). What actually keeps a registered player out of the world until they authenticate is the Paper pre-join dialog (`settings.registration.dialog.preJoin.enable`), which is on by default in 6.x.
- AuthMe 6.x split its jar per platform. `TYPE=PURPUR` needs the **Paper** jar; the Spigot one targets `spigot-1.21`, and the Folia/Velocity/Bungee jars are for other runtimes.
- The container's `${CFG_*}` substitution is a **plain text** replacement, not YAML-aware: a placeholder sitting in a *comment* is replaced too, which wrote the real `LINK_SERVICE_TOKEN` into a comment line. Keep placeholders out of comments — only the value line carries them.
- Every plugin request reaches the panel from the same container address, so `LINK_CLAIM_IP_LIMIT` (30/60s) is a **server-wide** budget for Minecraft linking, not a per-player one. LinkBridge's 3-second per-player cooldown exists to protect it.
- AuthMe logs "No supported permissions system found! Permissions are disabled!" — that is its own Vault/LuckPerms hook, not Bukkit permissions; `linkbridge.link` still defaults to true.
