## Project
- Rust (edition 2024) auth API: `POST /api/register`, `POST /api/login`, `POST /api/logout`, `GET /api/me`, account linking (`POST /api/link/start`, `GET /api/link`, `DELETE /api/link/{uuid}`, `POST /internal/link/claim`, `POST /internal/link/status`), player statistics (`GET /api/stats`, `POST /internal/stats/report`), and player inventory (`GET /api/players/{uuid}/inventory`, `POST /internal/inventory/report`, `POST /internal/items/icons`) on axum 0.8 + sqlx (Postgres) + argon2.
- All backend code lives in `src/main.rs` (no lib/module split). sqlx uses **runtime** queries, not `query!` macros — so there is no compile-time DB dependency.
- Everything else falls through to the static React build at `frontend/dist` (single `ServeDir` fallback route).
- A Caddy reverse proxy (`proxy` service, `dhi.io/caddy`, config in `Caddyfile`) terminates TLS and is the **only** published web service (host 80/443 → container 8080/8443). `app` publishes no ports — reach it through the proxy.
- A Minecraft stack runs alongside it: `velocity` (proxy) + `purpur` (backend), with **AuthMe** for in-game authentication and **LinkBridge** (a small Java plugin in `plugin/`) for account linking. See the Minecraft and LinkBridge sections below.
- Everything runs in Docker. The web stack uses hardened `dhi.io` images (requires `docker login dhi.io` first); the Minecraft services use community `itzg` images — a deliberate provenance tradeoff.

## Commands
- Run app: `docker compose --env-file .env.docker up --build -d` (served by the proxy at `https://localhost`; plain `http://localhost` 308-redirects to it). This starts **every** service, Minecraft included; the first boot downloads a server jar and generates a world, so `purpur`'s health stays `starting` for a minute or two. Add service names (`… up --build -d proxy app db`) to start only the web stack.
- Run tests: `docker compose --env-file .env.docker run --rm tests` (the `tests` service is behind the `tests` profile, so `up` never runs it)
- Build the Minecraft link plugin: `./scripts/build-plugin.sh` — Gradle in a container; installs the jar into `mc/purpur/plugins/`
- First-run Minecraft setup: `./scripts/mc-init.sh` — creates `.env.docker` if missing, generates `VELOCITY_SECRET` and `LINK_SERVICE_TOKEN`, creates `mc/`
- Export the whole stack: `./scripts/export.sh` — repo + `mc/` + a Postgres dump into `project-export-<timestamp>.tar.gz`
- Quick compile check: `cargo check --tests` — **the arbiter of truth. Never trust a claim about this code; verify it with this command.** It needs no running database, so it works on the host.
- DB shell: `docker compose --env-file .env.docker exec db psql -U postgres -d project_db`

## Environment & database
- `.env.docker` (never commit): `POSTGRES_PASSWORD`, `DATABASE_URL` (points at the `db` container hostname — it only resolves on the Compose network, so backend work must go through Compose, not host `cargo run`/`cargo test`), and `SITE_ADDRESS` (the proxy's public hostname; `localhost` uses Caddy's internal CA, a real domain triggers automatic Let's Encrypt). On a fresh clone create it from `.env.docker.example` and set your own password in both values. URL-encode special chars in passwords.
- `dotenvy::dotenv()` loads `.env` for non-Compose runs; Compose injects `.env.docker` via `env_file`. Keep the two in mind when a variable is missing.
- Schema lives in `migrations/` and is applied by sqlx automatically in `connect()` (runtime `Migrator`; reads `./migrations` relative to the process CWD — the Dockerfile copies it into the runtime image). Add a new numbered file; never edit an already-applied migration.
- `users` (`0001`): `id` identity PK, `name`, `surname`, `login` (UNIQUE), `login_displayed`, `email` (UNIQUE), `password_hash`; all TEXT NOT NULL. `sessions` (`0002`): `user_id` FK ON DELETE CASCADE, `token_hash` (UNIQUE), `created_at`, `expires_at`, `ip`, `user_agent`. `auth_rate_limits` (`0003`): `(scope, subject)` PK, `window_index`, `count` — per-IP fixed-window counters. `login_failures` (`0003`): `email` PK REFERENCES `users(email)` ON DELETE CASCADE, `failed_count`, `first_failed_at`, `locked_until`. `link_codes` (`0004`): `user_id` FK ON DELETE CASCADE, `code_hash` (UNIQUE), `created_at`, `expires_at`, `used_at`. `minecraft_accounts` (`0004`): `user_id` FK ON DELETE CASCADE, `uuid` (UNIQUE), `username`, `linked_at`. `audit_log` (`0004`): append-only `event`, `user_id` (nullable, **no** FK — the log outlives users), `detail`, `ip`. `player_stats` (`0005`): `uuid` PK, `username`, `play_seconds`, `blocks_placed`, `blocks_broken`, `first_seen_at`, `last_seen_at` — activity deltas the game server's plugin reports, added up per UUID. **No** FK to `minecraft_accounts` on purpose: stats outlive unlinking (unlinked rows are simply invisible; re-linking restores them). `player_inventory` (`0010`): `uuid` PK, `username`, `slots` JSONB (the 41-slot snapshot: storage 0–35, armor 36–39, off hand 40; a null entry is an empty slot), `updated_at` — the latest snapshot the game server reported, replaced wholesale on each report, and again **no** FK so it survives unlinking. `item_icons` (`0010`): `key` PK (an item registry key), `data_url` (a PNG data URL), `created_at` — item textures the plugin sends from the official Minecraft client textures packaged for the server version; the first upload for a key wins.
- Postgres string comparison is case-sensitive; email/login lookups rely on the app-level normalization below, not on the database.

## API semantics
- Register: `POST /api/register` → `202 {challenge, expires_in, email_delivery}` after sending a six-digit code (15-minute TTL); no user exists until `POST /api/register/confirm {challenge, code}` → `201`. Invalid/expired/used/exhausted codes → `400`; taken email/login → `409`; resend/mailbox/IP budgets → `429`; SMTP failure → `503`. Pending signups in migration `0011` hold Argon2 password hashes, SHA-256 challenge hashes and SHA-256(challenge:code), never raw codes/challenges. Five wrong attempts per code; 60-second resend cooldown; five emails per mailbox/hour. Confirmation creates a verified user and consumes the pending signup transactionally. Existing users retain their verification state and login access.
- Login accepts `{identifier, password}` with trimmed, lowercase email or login (legacy `{email, password}` remains supported). Email takes precedence on a cross-field collision; use the resolved account email for shared lockout/failure tracking. `200` success · `401` unknown email/login OR wrong password (intentionally identical — do not leak which accounts exist).
- Logout: `200` always; deletes the session row and clears the cookie (idempotent, no session required).
- Me: `200` with the current user, or `401` when the session cookie is missing, unknown, or expired.
- Rate limiting: `/api/login` and `/api/register` return `429` with a `Retry-After` header when the client IP is over its window budget. A locked account is **not** a `429` — it returns the ordinary `401`, indistinguishable from a wrong password.
- Linking: `POST /api/link/start` → `200 {code, expires_in}` (session). `GET /api/link` → `200 {accounts}`. `DELETE /api/link/{uuid}` → `204`, or `404` if it is not yours. `POST /internal/link/claim` (service token) → `200`; `404` for an unknown, used, or expired code (all identical); `409` when the UUID is already linked (the code is **not** consumed); `401` for a bad token; `503` when `LINK_SERVICE_TOKEN` is unset. `POST /internal/link/status` (service token) → `200` when the UUID is linked, `404` when it is not, `400` for a malformed UUID — bare codes and no body, so the plugin never parses JSON. `link_status` is deliberately **not** rate limited (unlike claim): it is a single indexed lookup behind the service token, and sharing the claim budget would let one busy login minute look like an attack and take real claims down with it.
- Statistics: `GET /api/stats` (session) → `200` with the user's own linked accounts, each carrying `stats` (null until the game server has reported anything for that UUID) and a `summary` across them — never another user's numbers. `POST /internal/stats/report` (service token) → `200`; `400` for an empty batch, more than 1000 players, a malformed UUID/username, or a counter outside `0..=4294967295` — the whole batch is rejected, nothing is stored; `401` bad token; `503` when `LINK_SERVICE_TOKEN` is unset. Deliberately **not** rate limited, like `link_status`: at most one batched request per flush from the game server's single container address. Reports are additive deltas; `first_seen_at`/`last_seen_at` are panel-observed times, not in-game timestamps. Since migration `0008` a report also carries `mobs_killed`, `deaths`, `distance_cm`, `items_crafted`, `fish_caught`, `damage_dealt`, `damage_taken`, `logins`, `items_picked_up`, `items_enchanted`, `tools_broken`, `animals_bred`, `times_slept`, `advancements` — all `#[serde(default)]`, so a report from a plugin jar that predates them is still accepted (missing = 0) and never clogged by a 400. Distance is hundredths of a block and damage is hundredths of a heart; the panel stores the reported integers and the website converts (blocks/km, hearts).
- Inventory: `GET /api/players/{uuid}/inventory` (session, owner-only, `Cache-Control: no-store`) → `200` with `{username, updated_at, slots}`; `slots` is **null** until the game server has reported one — never an invented inventory — and otherwise carries all 41 entries in game order (storage 0–35, armor 36–39, off hand 40), each item with `key`, `amount`, `damage`/`max_damage`, `display_name`, `enchantments`, and an `icon` data URL resolved from `item_icons` (null when none is stored); `401` without a session, `404` when the account is not the caller's. `POST /internal/inventory/report` (service token) → `200`; `400` unless the UUID/username are valid, there are exactly 41 slots, and every filled slot has a namespaced key, an amount in `1..=230`, `damage` and `max_damage` **together** (`0..=10000`, damage ≤ max), a name under 128 characters and at most 32 enchantments (`1..=32767`); `401` bad token, `503` unset. A snapshot **replaces** the previous one for that UUID instead of adding up. `POST /internal/items/icons` (service token) → `200`; `400` unless it holds 1–100 items with a unique namespaced key and a base64 PNG under 48 KiB, `401`/`503` as above; the first icon stored for a key is kept (a texture does not change under a running server). Both are deliberately **not** rate limited, for the same single-container reason as statistics.

## Conventions (follow these)
- `email` and `login` are normalized to **lowercase on write (register) and on sign-in lookup (email or login)**. `login_displayed` stores the original casing. Never add a lookup or write that skips normalization.
- Duplicate handling has two layers, **both required**: an early `SELECT 1 ... WHERE email=$1 OR login=$2` → 409, plus `is_unique_violation()` → 409 on the INSERT. The constraint is the real check; the SELECT is only an optimization (race window).
- Validation: name/surname/login/email non-empty after trim; login = ASCII alphanumeric + `_!@`; email via `email_address::EmailAddress::is_valid`; password at least 6 chars.
- Passwords: `Argon2::default()`, hash before INSERT, verify on login.
- Sessions: token = 32 random bytes (`getrandom::fill`) hex-encoded; store only its `sha2` SHA-256 in `token_hash`, never the raw token. 24h absolute TTL (`SESSION_TTL_HOURS`). Cookie `session=...; HttpOnly; Path=/; SameSite=Lax` with `Secure` unless `COOKIE_SECURE=false`. Protected handlers take the `SessionUser` extractor.
- Rate limiting/lockout: per-IP fixed windows live in `auth_rate_limits` (subject = `client_ip`, which trusts the `X-Real-IP` Caddy overwrites), enforced by `from_fn_with_state` middleware on `/api/login` and `/api/register`. Per-account backoff lives in `login_failures`, keyed by the normalized email. Never make a locked account distinguishable from a wrong password, and never record failures for unknown emails (unbounded table growth). Knobs: `LOGIN_IP_*`, `REGISTER_IP_*`, `LOCKOUT_*`.
- Linking: codes are single-use, stored only as `hash_token` (SHA-256), newest-only per user, TTL `LINK_CODE_TTL_SECONDS` (300). `claim_link` marks `used_at` inside a transaction so exactly one claim wins; a `409` (UUID already linked) rolls back and leaves the code usable. The service token is compared as SHA-256 digests with `constant_time_eq`, and the endpoint answers `503` when `LINK_SERVICE_TOKEN` is unset (fail closed). The panel stores only `user_id ↔ uuid/username` — never a Minecraft password.

## Minecraft (Velocity + Purpur)
- `velocity` (`itzg/mc-proxy`, `TYPE=VELOCITY`) is the only published Minecraft service (`25565`); `purpur` (`itzg/minecraft-server`, `TYPE=PURPUR`) publishes none and is reachable only through the proxy. Neither is a `dhi.io` image — community images, accepted with a provenance tradeoff.
- Offline ("cracked") mode on both sides: `online-mode = false` in `velocity.toml`, `ONLINE_MODE: "FALSE"` on the backend. Players are identified by offline UUIDs; the real gate is an in-game auth plugin.
- Modern forwarding: `player-info-forwarding-mode = "modern"` on Velocity; `proxies.velocity.{enabled,online-mode,secret}` in `paper-global.yml`. The secret comes from `VELOCITY_SECRET` in `.env.docker` (generated by `scripts/mc-init.sh`), is written to `mc/velocity/forwarding.secret`, and is interpolated into the backend config via `CFG_VELOCITY_SECRET`. Never commit it.
- Config layout: committed templates in `mc-config/` mounted read-only at `/config`; runtime state in `mc/` (gitignored) at `/server` (proxy) and `/data` (backend). `mc/` is the portable unit — worlds, plugins, jars, secrets.
- The backend sets `COPY_CONFIG_DEST=/data`, so `/config/<rel>` → `/data/<rel>` and `mc-config/purpur/` mirrors the server directory 1:1 (`config/paper-global.yml`, `plugins/AuthMe/config.yml`, `plugins/LinkBridge/config.yml`, …). Without that variable the attach point only reaches `/data/config`.
- **AuthMe** does in-game authentication — without it an offline server is impersonatable by anyone who types your name. Pinned by URL in `PLUGINS`. AuthMe 6.x ships **per-platform jars**; on Purpur use `AuthMe-6.0.1-Paper.jar` (not the Spigot/Folia/Bungee/Velocity ones).
- AuthMe's config is a **partial** file (`mc-config/purpur/plugins/AuthMe/config.yml`): ConfigMe fills every missing key from its defaults and rewrites the complete file, so only the keys we change are listed and it survives AuthMe upgrades. The `/config` sync overwrites the generated file each boot, so our values always win.
- `/website` must **never** be added to `settings.restrictions.allowCommands` — that list is for *unauthenticated* players. AuthMe already blocks all non-whitelisted commands before login; the plugin must additionally check `AuthMeApi.getInstance().isAuthenticated(player)`.
- `LINK_SERVICE_TOKEN` is generated by `scripts/mc-init.sh` and reaches the backend as `CFG_LINK_SERVICE_TOKEN` for the link plugin's config.
- `REPLACE_ENV_VARIABLES` / `REPLACE_ENV_DURING_SYNC` interpolate `${CFG_*}` only in files with the extensions `.yml`, `.yaml`, `.txt`, `.cfg`, `.conf`, `.properties` — extensionless files like `forwarding.secret` are **not** interpolated.
- `SYNC_SKIP_NEWER_IN_DESTINATION: "false"` forces the repo template to overwrite the server-generated config on every boot.
- `MC_VERSION` in `.env.docker` pins the backend version (`LATEST` or e.g. `26.3`); previously verified with Purpur `26.3-2652`; consult `STATE.md` for the latest deployment condition.

- Preserve the dependency-download settings in Compose: European Paper Maven mirror, HTTP/2 disabled for image downloads, and retained server libraries (AuthMe shares that directory). An interrupted jar must be checked against its provider checksum before restart.

## SkinsRestorer
- Pinned SkinsRestorer 15.12.6 is installed by Compose on Purpur only. The config template is `mc-config/purpur/plugins/SkinsRestorer/config.yml`.
- Intentionally backend-owned on this single-backend Velocity network: `server.proxyMode.detection: DISABLED`, `api: false`. Local file storage travels under `mc/`. Do not add a proxy installation without an AuthMe-aware command gate; proxy skin commands would bypass backend AuthMe restrictions.
- Keep skin commands and aliases out of AuthMe's pre-login allowlist. Skin lookup is cosmetic and must never replace authentication or alter offline UUIDs.
- `api.elyByEnabled: true` in release 15.12.6 tries Ely.by first and falls back to Mojang. A same-name Ely.by account has priority. TLauncher skins require a standard PNG import using `/skin upload` or `/skin url`; automatic launcher detection/import is unsupported. Client skin mods may override server-rendered skins.
- Website heads use the reported SkinsRestorer texture hash/model; saved acknowledges storage, not verified rendering on every client. See README's Skins section for commands and verification limits.

## Player skin uploads
- `GET /api/players/{uuid}/skin` and multipart `POST` are session-protected and owner-only (`404` otherwise), with `Cache-Control: no-store`. POST requires `X-Player-Skin: upload`, `file` and `model` (`classic`/`slim`). Fully decode the PNG, enforce ≤256 KiB and 64×64/64×32, then re-encode to strip metadata. Accepted uploads return `202`; active uploads `409`, accepted-upload cooldown (30 s) `429`.
- Migration `0009` stores observed `player_skins` separately (no link FK; survives unlink) and durable `skin_uploads` (FK cascades on unlink). Preserve `queued → signing → ready → saved` and `failed`; the SQL worker resumes after restart, retries network/server/rate-limit errors, has a ten-minute signing deadline and discards PNG bytes after success/failure. MineSkin receives unlisted images; optional `MINESKIN_API_KEY` comes from `.env.docker` and must never be committed.
- `/internal/skins/sync` and `/internal/skins/report` require the service token and public proxy block. LinkBridge 1.5.0 hard-depends on SkinsRestorer 15.12.6 and AuthMe. Serialized sync every 5 s processes up to 25 linked accounts, oldest checked first; it stores signed selections through SkinsRestorer while offline and touches live players only on the server thread after AuthMe authentication. An acknowledgement must match request ID and signed value before marking saved, so an old acknowledgement cannot complete a newer upload. Tests must explicitly clean observed skin rows, which outlive user deletion.

## LinkBridge plugin (`plugin/`)
- The in-game half of linking: `/website link <code>` → `POST /internal/link/claim`. One class, with AuthMe and SkinsRestorer supplied at runtime; the panel's `minecraft_accounts` table is the only record of a link, and the plugin never sees a password. Durable activity reports and server skin selections persist separately under `mc/`.
- `/website email` → `POST /internal/link/email` with the authenticated player's own UUID. Service-token-protected, proxy-blocked lookup returning only a masked plain-text email with `Cache-Control: no-store` (`404` unlinked, `400` malformed UUID). Shares the plugin's command cooldown with linking. Never accept a target-player argument, log/broadcast the hint, or deliver it after AuthMe logout/disconnect. This is a reminder only, not recovery or verification. The website copies the full `/website link <code>` command; standalone `/link` is not registered.
- After AuthMe authenticates a player, the plugin asks `POST /internal/link/status` and, only on `404`, tells them in chat that the account is not linked and where to link it (`panel-url`, which compose fills from `CFG_SITE_ADDRESS`). Any other answer — including an unreachable panel — is silent: a wrong "you are not linked" is worse than no message, and a linked player must never be nagged.
- The plugin also measures in-game activity for authenticated players (play time via a 10-second tick; `BlockPlaceEvent`/`BlockBreakEvent` counts; `EntityDeathEvent` kills, `PlayerDeathEvent`, `PlayerMoveEvent` distance capped at 8 blocks per move so teleports are skipped, `CraftItemEvent`, `EntityPickupItemEvent`, `PlayerFishEvent` catches, `EntityDamageByEntityEvent`/`EntityDamageEvent` final damage, `LoginEvent`/`RegisterEvent` sessions, `EnchantItemEvent`, `PlayerItemBreakEvent`, `EntityBreedEvent`, bed enter/leave pairs for `times_slept`, and `PlayerAdvancementDoneEvent` with a display) and reports **deltas since the last accepted report** to `POST /internal/stats/report` — every `stats-report-seconds`, on player quit, and synchronously (3 s timeout) in `onDisable`. Compute-send-mark is serialized on one lock so the timer and a quit flush never double-report; a non-`200` keeps the delta for retry, so a crash loses at most one flush. Activity before AuthMe login does not count — standing at the login gate is not playing. The panel adds deltas per UUID into `player_stats`; it never measures the game itself.
- The plugin also samples the **inventory** of every authenticated player on the server thread (Bukkit inventories may only be read there) every 5 s — storage 0–35 via `getStorageContents()`, armor via `getArmorContents()`, off hand — and reports the newest 41-slot snapshot to `POST /internal/inventory/report`: on any change, and re-sending an unchanged snapshot every `inventory-report-seconds` so the panel's "last seen" stays honest. A snapshot is current state, not a delta, and the accepted body is remembered per UUID, so a lost or unreachable send repairs itself on the next pass. Item textures are read from the plugin's packaged official Minecraft client assets at `assets/minecraft/textures/{item,block,item/armor}/<name>.png` and uploaded once per item key to `POST /internal/items/icons`; a key with no readable texture is marked accepted so it is never retried, and the website falls back to the sourced Performance Center artwork with the item name (never a generated icon). `onDisable` hands in the current inventory of everyone still online (3 s timeout), like the statistics flush.
- Layout: `plugin/src/main/java/dev/mcpanel/linkbridge/LinkBridgePlugin.java`, `plugin/src/main/resources/{plugin.yml,config.yml}`, `plugin/build.gradle`, `plugin/settings.gradle`.
- Built by `./scripts/build-plugin.sh`: Gradle 9 in `gradle:jdk25`, nothing installed on the host. The jar is installed into `mc/purpur/plugins/` (gitignored, so it travels with the server data and the target host never needs a JDK). `plugin/` is the committed source; `plugin/build/`, `plugin/.gradle/` and `.plugin-build/` are ignored.
- `plugin.yml` declares `depend: [AuthMe, SkinsRestorer]` and the command gates on `AuthMeApi.getInstance().isAuthenticated(player)`. That `getInstance()` returns **null** while AuthMe is not fully enabled, so the check must be `api == null || !api.isAuthenticated(player)` — fail closed. AuthMe's pre-login `allowCommands` whitelist is the other lock, and `/website` must stay out of it.
- Runtime config is `mc-config/purpur/plugins/LinkBridge/config.yml`: `api-base` (claim, status, email-hint, statistics, inventory and item-icon endpoints are derived from it), `panel-url: "https://${CFG_SITE_ADDRESS}/cabinet"`, `service-token: "${CFG_LINK_SERVICE_TOKEN}"`, `cooldown-seconds`, `stats-report-seconds` (statistics flush interval), `inventory-report-seconds` (how often an unchanged inventory is re-sent), `timeout-seconds`. Keep placeholders out of its comments (see Traps).
- The JDK **must** match the backend's Java: `paper-api` 26.3 is Java 25 bytecode (class file major 69) and an older javac refuses to read it. Use Gradle, not raw `javac` — `paper-api` needs ~20 transitive jars (Adventure, annotations, bungee-chat, …) before its signatures resolve.
- The version lives in `plugin.yml` and is passed to Gradle as `-PpluginVersion`. Keep `paper-api` in `build.gradle` in step with `MC_VERSION`, and `AUTHME` in the script in step with `PLUGINS`.
- Claim and status answer with bare status codes. Email-hint success returns only a masked plain-text address. The plugin maps status codes to messages and never parses JSON. Claim's `404` covers unknown, used **and** expired codes on purpose.

## Testing (`#[cfg(test)] mod test` in src/main.rs)
- All tests hit real Postgres and run in parallel — they must be idempotent.
- Run via the Compose `tests` service (mounts the repo, runs `cargo test`): host `cargo test` cannot resolve the `db` hostname.
- Rules: random 16-char `Alphanumeric` identifier per run; emails as `test_{random}@example.com` **lowercased**; after every inserting sub-case, `DELETE ... WHERE email=$1` **before** the assert, binding the **stored (lowercase)** form — the cleanup value must match what the app stores, not the raw input. `player_stats` has no FK to the user, so `delete_user` cannot reach it — tests that post a `stats` report must `DELETE FROM player_stats WHERE uuid = $1` for each UUID they reported. `player_inventory` and `item_icons` are the same shape: clean `DELETE FROM player_inventory WHERE uuid = $1` and `DELETE FROM item_icons WHERE key = $1` (lowercased) for anything a test stored.
- A new test must survive: repeated runs, parallel execution, and a run that failed mid-test (no leftover rows).

## Traps (learned the hard way)
- `rand` is **0.10**: `sample_iter` / `random_range` live on `RngExt`, not `Rng`; `random_string` / `random_char` were removed in 0.10 (they existed in 0.9). Build random strings with `sample_iter(Alphanumeric)`.
- tower-http 0.7's `ServeDir::not_found_service` wraps the fallback in `SetStatus` and **forces the response to `404`** — the correct body with the wrong status. An SPA needs `ServeDir::fallback`, which preserves the fallback's status. The old symptom was `/cabinet` returning the shell with a `404`, which browsers render anyway, so it looked fine while being a lie about the resource.
- `Alphanumeric` includes A–Z — anything bound directly to SQL (test cleanups, lookups) must be lowercased first.
- The `email_address` crate accepts single-label domains by default (`x@exa` is "valid") — do not assume TLD enforcement.
- `let _ = expr?;` is an antipattern — `?` already propagates the error; use the bare `expr?;`.
- Never run `docker compose down -v` — it deletes the `pgdata` volume and all database data. Plain `down` keeps it.
- Caddy in `dhi.io/caddy` runs as UID 65532, so it **cannot** bind 80/443: the `Caddyfile` sets `http_port 8080`/`https_port 8443` and Compose maps host 80/443 onto them. Do not "fix" the Caddyfile to listen on 80/443 — it will fail on a real Linux host (Docker Desktop happens to allow low ports, which hides the bug).
- Caddy sends HSTS everywhere except `localhost` (matcher in `Caddyfile`) — otherwise a local `https://localhost` visit would force HTTPS on every other localhost dev server (e.g. Vite).
- Caddy **overwrites** `X-Real-IP` / `X-Forwarded-For` with the real peer address (verified: a spoofed value does not survive), so `client_ip` can trust them. Do not delete the `header_up X-Real-IP` line in the `Caddyfile`.
- Behind Docker Desktop every request reaches the app from one NAT address, so the per-IP limit acts globally on a Mac. That is an artifact of the local network, not a bug.
- Tests send a random `X-Real-IP` per request (see `send_from`) so the per-IP limiter cannot bleed across parallel tests; the rate-limit tests pass a fixed IP and clear their own rows.
- `rand` is test-only and lives in `[dev-dependencies]`; production randomness (session tokens) uses `getrandom::fill`.
- sqlx's runtime `Migrator` reads `./migrations` from the process CWD, so it only finds them when the app/tests start from the repo root (`/app`) — there is still no compile-time DB dependency.
- `AGENTS.md` is **tracked** in this repo (it is *not* gitignored here); `.gitignore` ignores `.env*` except `.env.docker.example` — there is no committed `.env.example`. Keep secrets out of git.
- `/internal/*` is blocked **twice**: `handle /internal/* { respond 404 }` in the `Caddyfile` (so it is never public) and the `LINK_SERVICE_TOKEN` check in `claim_link`. Keep both. The `handle` blocks are deliberate — do not collapse them back into a bare `reverse_proxy`, or `/internal/link/claim` becomes reachable from the internet.
- `audit_log` has **no** FK to `users` (it must outlive them), so deleting a test user leaves its audit rows behind — tests use the `delete_user` helper, which removes audit rows for that user first.
- The `tests` service sets `LINK_SERVICE_TOKEN: test-service-token` in `compose.yaml`; without it the claim tests would get `503`. Host `cargo test` still lacks it.
- `mc-proxy` merges Velocity's bundled default `velocity.toml` **under** our file, and Velocity 4.x's default ships **uncommented** example `forced-hosts` (`lobby.example.com`, `factions.example.com`, …). Without an explicit empty `[forced-hosts]` (merged to `forced-hosts = {}`) Velocity refuses to start: "Server 'lobby' for forced host 'lobby.example.com' does not exist".
- `ci.pufferfish.host` — the only source the itzg image uses for `TYPE=PUFFERFISH` — returns `502`, and the project looks stale (no commits since 2025-12-21, branches stop at `ver/1.21`). `TYPE=PUFFERFISH` therefore crash-loops with `jq: syntax error … error code: 502`. Purpur is the stand-in; switching back is a one-line `TYPE` change.
- Do **not** name a Minecraft service `proxy` — the Caddy service owns that name. Minecraft's `25565` does not collide with Caddy's 80/443.
- Verified: a client connecting straight to the backend is answered with a `velocity:player_info` login-plugin request and dropped, while a login through Velocity returns Login Success. Keep the backend port unpublished — that plus forwarding is the whole trust model.
- AuthMe's `ProtectInventoryBeforeLogIn` is silently **disabled without PacketEvents** ("WARNING! The protectInventory feature requires PacketEvents! Disabling it..."). What actually keeps a registered player out of the world until they authenticate is the Paper pre-join dialog (`settings.registration.dialog.preJoin.enable`), which is on by default in 6.x.
- AuthMe 6.x split its jar per platform. `TYPE=PURPUR` needs the **Paper** jar; the Spigot one targets `spigot-1.21`, and the Folia/Velocity/Bungee jars are for other runtimes.
- The container's `${CFG_*}` substitution is a **plain text** replacement, not YAML-aware: a placeholder sitting in a *comment* is replaced too, which wrote the real `LINK_SERVICE_TOKEN` into a comment line. Keep placeholders out of comments — only the value line carries them.
- Every plugin request reaches the panel from the same container address, so `LINK_CLAIM_IP_LIMIT` (30/60s) is a **server-wide** budget for Minecraft linking, not a per-player one. LinkBridge's 3-second per-player cooldown exists to protect it.
- AuthMe logs "No supported permissions system found! Permissions are disabled!" — that is its own Vault/LuckPerms hook, not Bukkit permissions; `linkbridge.link` still defaults to true.

## Coins
- Migration `0007` adds `player_stats.coins` (zero initially; no historical backfill) and permanent `stats_reports` deduplication receipts. One authenticated, uncancelled block break earns one coin, in the same transaction as its reported activity.
- Statistics reports require a UUID `report_id`; replaying the same normalized payload is a no-op (`200`), conflicting payloads return `409`. Never prune receipts without a replacement deduplication protocol. Tests must clean their receipts as well as UUID statistics.
- LinkBridge persists an immutable outgoing report in its plugin data folder before sending; retries/restart replay it. Unsaved activity can still be lost on a hard crash. Default flush is 5 seconds; the website refreshes every 5 seconds.
- `/balance` (alias `/bal`) is authenticated, own-account only, shares the website-command cooldown, flushes earnings first, then calls service-token-protected `POST /internal/balance` (`{uuid}` → plain-text coins, no-store). No balance is invented during a sync failure. Keep these commands out of AuthMe's pre-login whitelist. UUID balances outlive links and accrue even before linking.
